# Tenant regression, pilot capacity and review policies

SaaS-016, 2 November 2026. Scoped company writes now enforce fixed pilot admission caps atomically. Company Owners/Admins can review aggregate capacity and policy; only an active Owner with current-password proof can change retention-review periods, legal hold and audit-download controls. This is a locally verified private-pilot foundation, not approval to launch unrestricted public signup or charge customers.

## Capacity and atomicity

| Resource | Pilot cap | Admission / counting rule |
| --- | --- | --- |
| Companies | 10 retained companies per deployment database | Seeded PilotGates row 1 locks fleet admission across API processes; existing legacy companies count too |
| Company creation by an Owner | Refuse creation when already active Owner of 3 companies | Checked under the same fleet gate; ownership transfers are not blocked by this creation threshold |
| Active company members | 25 including Owners/Admins/Members/Guests | Reactivation checks under the company gate; future invitations must use the same gate/check before admission |
| Active projects per company | 20 | Scoped create checks under the company gate |
| Active tasks per company / project | 2,000 / 500 | Scoped task create checks after project access under the company gate, across every project in the company |
| Retained projects / tasks per company | 100 / 10,000 | Deleted content still consumes retained capacity, preventing create/delete loops |

Active means not soft-deleted for content, irrespective of To Do/In Progress/Completed status. Tasks in deleted projects stop consuming active capacity but still consume retained capacity. Suspended/removed members stop consuming active seats. No over-limit existing content is deleted or hidden by quotas; existing reads, edits, cleanup and ownership safeguards remain available. Restored/imported companies above a cap require operator reconciliation before new allocation. The fixed values come from the proposed pilot profile and are operating guardrails, not paid-plan entitlements or customer-approved service commitments.

The count check and business/audit insert commit in the same transaction. Competing requests for the final slot produce one successful allocation and a 409 `quota.exceeded`, with no rejected mutation/success audit. Gates are database rows, not per-process counters. Company creation locks only the seeded fleet gate before counting; normal scoped writes serialize on their existing company row, so they do not take a fleet lock. The application fails closed if the admission row is missing. Runtime needs SELECT and UPDATE(Id) for the fleet locking read on the verified MySQL setup; it has no gate INSERT/DELETE permission. A direct isolated privilege probe established that SELECT alone fails and SELECT plus UPDATE(Id) succeeds. The app never changes that row.

Legacy v1 resource APIs and nullable-scope compatibility remain explicit cutover debt. Pilot quota guarantees apply to scoped v2 writers; run the pilot with all three workspace flags enabled so lifecycle retirement closes v1 resource access. Do not mix old/unscoped/raw writers with quota-controlled admission. Maintenance backfill/operator SQL can exceed caps intentionally and must be reviewed; runtime queries do not infer or merge missing scope. Existing flags remain default off. Public onboarding still awaits R2 identity/mail/invitations; fleet caps are not signup verification.

## Policy API and privacy

GET `/api/v2/workspaces/{workspaceId}/policy` requires active Owner/Admin membership and returns policy revision, review settings, `automaticPurgeEnabled: false` and aggregate capacity. These administrative counts include private projects but expose no private names, descriptions, individual assignments or project IDs. Other company members/guests cannot read these aggregates. This is a deliberate capacity-administration permission, not a company-admin private-project content override. Ordinary dashboard/project/audit access still uses explicit grants.

PUT on the same route requires active Owner membership, paired CSRF, current-password proof for real changes, and the policy `expectedVersion` string. Supported audit review periods are 90/180/365/730 days; deleted-content review periods are 30/90/180/365 days. Boolean fields and both periods must be supplied explicitly; unknown properties and query parameters are rejected. Stale settings return 409, unsupported periods return validation errors. A no-op does not change the revision or create business history/proof. The governance limiter is shared with sensitive lifecycle actions. Revision, settings and safe CompanyPolicyChanged deltas commit together; failed audit persistence rolls back all settings while independently completed password-proof facts remain security events.

Defaults are 365-day audit review, 30-day deleted-content review, legal hold on and company audit exports enabled. A hold marks the company for retention, not deletion. These are manual-review preferences: **there is no automated purge, deletion schedule, erasure guarantee, account closure or external archive in this release**. Shortening a review period does not hide history or delete records. Governed purge, grace periods, backup handling and company closure remain SaaS-045 and related storage/worker work. No jurisdictional/legal compliance claim follows from these settings.

Disabling audit downloads has immediate next-request enforcement at both protected-ticket creation and download inside the authorized read snapshot. Previously issued tickets confer no override. The audit console exposes the current export bit and disables its download button while still allowing permitted history review. This controls packaged downloads, not copying already readable content. In-flight authorized snapshots retain the existing read semantics. Platform SecurityEvents and restricted operations exports are independent of company policy and never exposed to company administrators.

## Deployment and evidence

The migration adds review fields to Workspaces and the single gate table; it does not delete content/history. Existing project/task revisions remain intact. Use the migration identity; runtime never seeds a missing gate. Stop old writers, take verified DB/key backups, migrate in maintenance and deploy matching frontend/backend. MySQL DDL can partially commit; recovery uses reviewed forward repair or restore, not online Down.

A populated synthetic backup is restored and upgraded to all seven migrations, with a no-op second run, preserved counts/history/revisions and default hold/export settings. Run current backfill tools only against all migrations compiled into that tool; expansion-only historical binaries are not interchangeable with the current model. Local published HTTPS rehearsals use actual restricted runtime/operations grants and synthetic fixtures only; no running user database or service is changed.

The browser pilot journey confirms capacity cards, password/confirmation, persisted settings, safe audit deltas, old-ticket denial, disabled download UI and a quota rejection that retains its draft, with four desktop/mobile accessibility scans. It also records a bounded eight-worker, 480-request scoped hot-company regression at the project cap, including expected stale-revision conflicts without replay. This measures local behavior, not representative full-pilot sizing, cross-company fairness, selected-host capacity or an SLA.
